🐔 Poultry Disease Detector — CYD HMI

Embedded poultry-health monitoring and disease-detection interface built around an ESP32 CYD, LVGL 9.3, EEZ Studio, and UART telemetry from an STM32 controller.










📌 Overview

The Poultry Disease Detector — CYD HMI is the graphical human-machine interface (HMI) for an embedded poultry monitoring system.

The CYD (Cheap Yellow Display) acts primarily as a display and user-interface terminal. Environmental and device telemetry is supplied by an STM32 controller over UART, while AI disease results can be integrated from the system's Raspberry Pi/AI pipeline.

The interface is designed with EEZ Studio and rendered using LVGL 9.3.

Core responsibilities

🌡️ Display temperature

💧 Display relative humidity

🌬️ Display atmospheric pressure

🧪 Display ammonia / MQ-135 reading

🔋 Display battery percentage

⚡ Display charging state

🐔 Display poultry disease classification

🎯 Display AI confidence

🖥️ Provide a clean embedded HMI

🔌 Receive telemetry from the STM32 over UART

Architectural principle

The project follows a separation-of-concerns model:

Layer

Responsibility

STM32

Sensor acquisition, battery monitoring, system control and telemetry generation

UART Driver

Receives and parses STM32 telemetry

Telemetry Model

Holds the latest system values

UI Manager

Converts telemetry into display updates

EEZ Studio

Defines screens, widgets, positions and visual design

LVGL 9.3

Runtime graphics/UI engine

ESP32 CYD

HMI processor and display controller

Raspberry Pi

Camera processing, AI inference and cloud connectivity

This keeps generated UI code separate from application logic and makes it possible to change the communication layer without redesigning the interface.

🔌 UART Telemetry

The CYD receives telemetry from the STM32 through Serial2.

Current configuration

Parameter

Value

Interface

ESP32 Serial2

Baud rate

9600

Data bits

8

Parity

None

Stop bits

1

TX

GPIO 27

GPIO 22

Protocol

Line-based ASCII

Packet terminator

\n

Packet format

#TEMPERATURE,BATTERY,HUMIDITY,PRESSURE,MQ135,CHARGING\n

Example:

#29.4,75,68.2,1012.7,15.4,1

The CYD interprets this as:

Temperature   = 29.4
Battery       = 75 %
Humidity      = 68.2 %
Pressure      = 1012.7
MQ135         = 15.4
Charging      = TRUE

UART data flow

sequenceDiagram
    participant STM as STM32
    participant UART as UART Driver
    participant DATA as TelemetryData
    participant UI as UI Manager
    participant LVGL as LVGL 9.3
    participant TFT as CYD Display

    STM->>UART: #29.4,75,68.2,1012.7,15.4,1\n
    UART->>UART: Receive + parse
    UART->>DATA: Update telemetry
    UART-->>UI: New packet available
    UI->>LVGL: Update labels/icons
    LVGL->>TFT: Render updated screen

🧱 Design Pattern

This project intentionally uses a lightweight layered architecture:

flowchart TB
    A[Hardware Inputs] --> B[Communication Layer]
    B --> C[Data Model]
    C --> D[Application/UI Layer]
    D --> E[LVGL]
    E --> F[Display]

    G[EEZ Studio] --> E

Why?

It prevents hardware communication and UI code from becoming tightly coupled.

For example, if UART is later replaced with:

CAN

RS-485

SPI

Wi-Fi

BLE

the UI Manager can remain unchanged as long as the new communication layer populates the same TelemetryData structure.

🛡️ Recommended Future UART Protocol

The current ASCII protocol is excellent for early development because it is simple and easy to debug.

For production, a framed protocol is recommended:

┌──────┬──────┬──────┬──────────────┬───────┬──────┐
│ SOF  │ TYPE │ LEN  │ PAYLOAD      │ CRC   │ EOF  │
├──────┼──────┼──────┼──────────────┼───────┼──────┤
│ 0xAA │ 0x01 │ 0x.. │ telemetry... │ CRC16 │ 0x55 │
└──────┴──────┴──────┴──────────────┴───────┴──────┘

This would protect the display from corrupted or incomplete UART packets.

Possible future features:

CRC16

packet type

payload length

sequence number

device status

protocol version

📊 Telemetry Model

The application should maintain a single source of truth:

struct TelemetryData
{
    float temperature;
    float humidity;
    float pressure;
    float ammonia;

    int32_t batteryPercent;
    bool charging;

    DiseaseType disease;
    uint8_t confidence;

This gives the rest of the application a clean interface regardless of where the data originates.

🧑‍💻 Development Guidelines

1. Do not edit generated EEZ files unnecessarily

Files generated by EEZ Studio may be overwritten during regeneration.

Prefer:

Application logic
    ↓
ui_manager.cpp

instead of placing custom application logic inside:

src/ui/screens.c
src/ui/styles.c
src/ui/images.c

2. Keep communication separate from UI

Bad:

uart_slave_read()
{
    ...
    lv_label_set_text(...);
}

Better:

uart_slave_read()
{
    ...
    telemetry.temperature = ...;
}

followed by:

uiManagerUpdate(telemetry);

3. Keep LVGL calls in the UI layer

This makes the firmware easier to maintain and test.

🐛 Troubleshooting

LVGL compilation errors

Verify that the project is using the intended LVGL version:

pio pkg list

Look for:

lvgl @ 9.3.x

The project is intentionally built around LVGL 9.3.

Display is blank

Check:

lv_conf.h

TFT_eSPI configuration

Setup_ESP32_2432S028R_ILI9341.h

display dimensions

SPI pins

initialization sequence

LVGL tick configuration

lv_timer_handler() execution

UART data is not appearing

Check:

STM32 TX → ESP32 RX
STM32 RX ← ESP32 TX
STM32 GND ─ ESP32 GND

Also verify:

9600 baud
8 data bits
No parity
1 stop bit

and ensure each packet ends with:

\n
